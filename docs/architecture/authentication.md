# Authentication and sessions

English | [简体中文](authentication.zh-CN.md)

`POST /v1/auth/bind` accepts an optional hexadecimal Steam Encrypted App Ticket. Without it, legacy clients remain compatible but receive a session-scoped `unverified` identity. When present, the backend sends the ticket through stdin to a separately deployed verifier and issues a session-scoped `verified` identity when decryption succeeds and the decrypted SteamID matches the requested SteamID. AppID, issue time, VAC state, and ticket reuse are not acceptance criteria. A supplied ticket never silently degrades: decryption failure, an invalid decrypted SteamID, or a request/ticket SteamID mismatch is rejected.

The verifier executable is invoked directly without a shell or ticket command-line argument. Runtime, stdin, stdout, and stderr are bounded. The standalone Go verifier dynamically loads Valve's platform-native `sdkencryptedappticket` library and reads the 32-byte title key from a separate environment value or read-only file; neither the native library nor key is compiled into the control plane. AppID, issue time, and VAC state are collected only as best-effort metadata and failures to read them do not invalidate a decrypted ticket. The backend never stores ticket plaintext; when optional metadata is available, `auth_steam_ticket_verifications` stores a deduplicated SHA-256 ticket hash, authoritative SteamID, AppID, issue time, player ID, and verification time for audit. A duplicate hash does not reject a bind. The matching ticket SteamID is used to create or load the player.

Structured device fingerprints accept `uuid|disk|cpu` as well as `v1|uu:<16hex>|ds:<16hex>|cp:<16hex>`. PostgreSQL stores no raw SMBIOS, disk, CPU, or composite fingerprint text. `auth_device_fingerprints` contains a domain-separated HMAC-SHA-256 composite digest and independent factor digests, identified by a stable key ID; sessions and login/risk events reference that record. `ban_device_fingerprint` restricts a bind only when at least two factors from one ban row match. Legacy opaque Device IDs without pipes remain accepted and continue to use the existing SHA-256 session/risk hash and four-character display suffix, but cannot be split retroactively.

`DEVICE_FINGERPRINT_HMAC_KEY_BASE64` is an independent, long-lived secret containing at least 32 random bytes. Production refuses to start without it. The corresponding `DEVICE_FINGERPRINT_KEY_ID` is stored beside each digest. Because raw factor values are deliberately discarded, old rows cannot be recomputed after losing or changing this key; back it up and design an explicit multi-key transition before rotation. Do not reuse JWT, Relay, update-signing, database, or administrator secrets for this purpose.

The Access Token is a short-lived Ed25519 JWT bound to a database session. It includes `user_id`, `auth_level`, and `steam_verified`; the session row is authoritative so an unverified bind cannot inherit a previously verified player's privileges. Refresh Tokens are opaque random secrets stored as hashes. A successful refresh atomically revokes the old token, preserves the session authentication level, transfers the in-memory integrity ticket state, and issues a replacement in the same family. Reuse of any rotated token revokes the family, records a high-severity event, increments `auth_refresh_reuse_total`, and requires a new bind. Logout and session-management APIs revoke database state, so previously signed Access Tokens stop authenticating.

For a verified bind, the decoded encrypted ticket bytes are kept only in process memory until the initial proof completes or the session state expires. The bind response and every `POST /v1/integrity/challenge` call return a fresh 32-byte hexadecimal nonce and invalidate the previous nonce. An untrusted bind session uses a constant-time comparison of `SHA256(toolbox_pem_file_bytes || encrypted_ticket_raw_bytes || nonce_ascii)`; a trusted session uses `SHA256(toolbox_pem_file_bytes || nonce_ascii)` and first matches the session's persisted `SHA256(toolbox_pem_file_bytes)` fingerprint. Success persists `integrity_trusted` and refresh copies it with the fingerprint, so trusted sessions can be challenged after a process restart without a ticket. Every failure immediately clears session integrity trust; three consecutive failures revoke the session and create `INTEGRITY_FAILED` audit and risk records. A matching banned hardware fingerprint raises the terminal risk severity to critical.

The ToolBox certificate is read from `TOOLBOX_PUBKEY_PATH` (preferred) or `TOOLBOX_PUBKEY`. The exact PEM bytes participate in the hash, including line endings, so operators must mount the same canonical file used by the client build pipeline. Challenge state and ticket plaintext are never written to PostgreSQL and are intentionally lost on a process restart. A trusted session can receive a new ticketless challenge from its persisted trust and fingerprint; only an untrusted session whose bind-time ticket was lost receives an empty nonce and must bind again.

Invite codes are generated outside logs, stored as hashes, bounded by expiry and quota, and consumed in the same PostgreSQL transaction as player/session creation. Concurrent use cannot exceed `max_uses`. Administrator responses may return plaintext only once at creation; list/revoke responses do not.
